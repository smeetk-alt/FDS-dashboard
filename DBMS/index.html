TRUNCATE vs DELETE vs DROP

        
DELETE removes rows one at a time, is logged, and can be rolled back. TRUNCATE removes all rows at once without row-by-row logging, resetting the table fast. DROP removes the table definition itself, including its schema, not just the data.

WHERE vs HAVING

        
WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY has produced them, so it can reference aggregate results like COUNT(*) that WHERE cannot see.

Updating through a view

        
A view is a stored query, not stored data. Updating through a view that joins multiple tables or uses aggregates is ambiguous (which base table does the change belong to?), so most engines restrict updatable views to simple single-table projections.

Experiment 7

      
Access Control

      
RBAC / DAC simulation - MediTrack's own navigation enforces this: compare what Admin, Doctor and Patient can each see.

      

        RBAC
        DAC
        MAC
        GRANT / REVOKE
      


      

        

          
R

          
RBAC

          
Role-Based Access Control. Permissions attach to a role (Admin, Doctor, Patient), and users inherit whatever their assigned role can do. This is exactly how MediTrack's own sidebar works.

        

        

          
D

          
DAC

          
Discretionary Access Control. The owner of an object grants or revokes privileges directly on it with GRANT / REVOKE, optionally letting the grantee re-grant it with WITH GRANT OPTION.

        

        

          
M

          
MAC

          
Mandatory Access Control. A central authority assigns a classification level to data and a clearance level to users; access is allowed only when clearance meets or exceeds classification, regardless of ownership.

        

      


      
Role → page access matrix

      

      
Equivalent SQL (DAC)

      
GRANT SELECT, INSERT, UPDATE ON patient TO doctor_role;
GRANT SELECT ON patient TO patient_role;
REVOKE UPDATE ON patient FROM patient_role;
GRANT SELECT ON doctor TO patient_role WITH GRANT OPTION;

      

        
Access Control List vs Access Control Matrix

        
An Access Control List (ACL) is stored per object: each table keeps its own list of which roles can do what to it. An Access Control Matrix is the conceptual whole-system view: rows are subjects (roles/users), columns are objects (tables/views), and each cell is the set of permitted operations. ACLs are one efficient way to store that matrix's columns.

Reading the plan

        
Before the index, the plan says SCAN patient, meaning every row is checked. After CREATE INDEX, SQLite's planner switches to SEARCH patient USING INDEX idx_disease, jumping straight to matching rows via a B-tree lookup instead of scanning the whole table.

      

    


    
    

      
Experiment 9

      
Transactions & ACID

      
BEGIN / COMMIT / ROLLBACK, demonstrated on a ward-transfer.

      

        BEGIN
        COMMIT
        ROLLBACK
        Isolation level
      


      

        
A
Atomicity
The patient transfer below runs both UPDATEs as one unit. Either both succeed, or neither does, so a bed is never freed in one ward without being taken in the other.

        
C
Consistency
The CHECK (salary > 0) constraint from Experiment 3 and foreign keys guarantee the database moves between valid states only.

        
I
Isolation
Concurrent transactions should not see each other's uncommitted changes. SQLite's default is Serializable for a single connection; PostgreSQL defaults to Read Committed.

        
D
Durability
Once COMMIT returns, the change survives a crash. ROLLBACK below demonstrates the opposite: an uncommitted change is fully undone.
